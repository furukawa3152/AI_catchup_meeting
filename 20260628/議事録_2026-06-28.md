## 1. モデルの使い分け（Claude / Codex の協調）

複数モデルを併用した開発スタイルについて議論があった。

- 当初は単一モデル（Claude系）で開発していたが、すぐにコンテキスト上限に達するため、別系統のモデル（Codex系）も併用するようになったという事例が共有された。
- 体感として、レビューに回すと「ここに問題がある」という指摘が次々に出てくる。指摘を受けて修正させても、片方のモデルがなかなか直しきれず、何往復もすることがある。
- 一方のモデルは、レビュー指摘に対して「ごもっともです」と全面的に受け入れる傾向があり、もう一方は反論することがある、という挙動の違いが観察された。
- 試行錯誤の結果、効率的だと感じた進め方:
  1. まず一方のモデルに全体を作らせる
  2. もう一方にレビュー・問題箇所の修正をさせる
  3. 最後に元のモデルに戻して最終レビューさせる
- 副作用として、相互チェックを挟むと「なかなか前に進まなくなる」という課題も挙がった。

### 論点・補足意見

- 「モデルの優劣以前に、実装に必要な情報を与えられているかが本質的な問題ではないか」という指摘。
- 継ぎ足しで積み上げてきたコードを後から別モデルに丸ごと見せると、構造そのものへのツッコミが出やすい。それは「ミス」というより設計・経緯に起因する可能性がある。
- 「混ぜると危険」という意見も出た。モデルを混在させると、どちらも正解でない可能性もあり得る。特に明確な正解が定まらない（抽象度のある）処理では判断が難しい。
- 別アプローチとして、あるエージェントから別のエージェントを呼び出すプラグイン的な仕組みでレビューさせると、コンテキストを保ったまま別モデルの思考を使えるため有効、という話も紹介された（コンテキストを外部に出している可能性がある、という推測込み）。
- 「やったと言って実際にはやっていない」挙動が話題に。バージョンが上がるごとに減るとされるが、別モデルでチェックすると指示の抜け漏れが見つかることがある。

## 2. フロントエンド生成サービスの所感

UI/フロントエンド特化の生成サービスを触った所感が共有された。

- 内部で動いているのは汎用の大規模モデルだが、フロントエンド（Reactベース）生成に必要な指示・前提がアプリ側に作り込まれているため、自然言語の簡単な指示で「AIっぽくない」気の利いたUIを段取りよく生成してくれる。
- 提供元があらかじめ画面構成のテンプレートを保持しており、「一から自分で構築するか／用意されたものを触るか」の違い、という整理がなされた。
- 結論的な気づき: どのエージェントを使うにせよ、「何を作らせたいか」という前提条件を徹底的に詰めて与えれば、特化サービスでなくても同様の成果が得られるのではないか。

## 3. クラウド経由でのモデル利用とセキュリティ

- 企業では「生成AIに社内情報・個人情報を入力してはいけない」という制約があることが多い。
- 利用にあたっては、サービスの利用規約を確認し、「どの国の法律が適用されるか」「入力情報がどこで処理されるか」を把握しておくべき。
- 主要クラウド各社（AWS / Google Cloud / Microsoft Azure）が、それぞれのクラウド上でモデルを提供している。
- コーディング用ツールの接続先を、提供元への直接契約ではなく、契約済みクラウド側に切り替えることが可能。これにより情報が自社契約クラウド内に閉じ、セキュリティ／情報システム部門が許可する範囲での取り扱いが可能になる。
- 直接契約できない場合でも、各クラウド経由でモデルを利用する選択肢がある。あるクラウドベンダーと大手AI企業の提携により、当該クラウド上で別系統のコーディングツールも動くようになった。

### 補足

- このため「モデル名で呼ぶ」のが適切とは限らず、どのサービス／どの会社経由で利用できるかという文脈が重要になる。

## 4. ノーコードツールとAIの相性

- 業務でノーコードツール（kintone、Googleワークスペース内の表計算系サービス、ファイルメーカー等）を扱う立場から、「AI時代にノーコードが一番しんどい」という共感が広がった。
- 理由: 同じ機能なら一からWebアプリとして生成すれば一瞬なのに、ノーコードでは独自ルールに従ってGUIをポチポチ操作する必要がある。ガスでのWeb開発に比べ「30倍くらい時間がかかる」感覚。
- メンテナンス負荷の懸念も挙がった。

### 開発を楽にするコツ（共有された実践知）

- 公式提供のMCPを導入すると体感が大きく変わる。テストコード生成などにも対応。
- ブラウザの開発者ツール（DevTools／コンソール）連携のMCPを併用し、操作時の内部処理・状態変化をAIに読み取らせると、開発効率が大きく向上する。
- マイナーなノーコード製品でも、最新の汎用モデルは独自スクリプトや画面ルールをかなり把握している。スクリーンショットを与えて「これがやりたい」と伝えると、的確な回答・スクリプト記述・リファクタリングが得られるようになってきた。
- 半年前は難しかった独自スクリプトの取り扱いも、現在は精度が向上している。

### 展望に関する議論

- これだけAIで開発できると、個人利用レベルではノーコード専用ツールの優位性が薄れているのではないか。
- 一方、日本企業ではレガシーに作り込まれた環境からの脱却が難しく、既存ツールが残り続けるケースも多いだろう。
- MCP等が充実し、AIから直接開発できる方向に進まないと淘汰されうる、という見方。

## 5. 画像・動画生成、アバター

- 画像生成サービスで素材を作り、別ツールで並べてナレーションを入れ、紙芝居風の動画を制作した事例が共有された（実写は表現上の制約があるためアニメ風で対応）。
- 「自分の顔・声を読み込ませて自由に喋らせる」用途について議論。
  - あるサービスのアバター機能はテンプレートの顔のみカスタマイズ可能で、実在しない人物のリアルな顔・多様な声が用意されている。本人の顔取り込みは提供されていない。
  - 個人向け契約側にはアバター機能が降りてくる可能性があるが、法人ワークスペース側では悪用リスク等から提供されない可能性が高い、との見方。
- あるクラウドベンダーは、静止画を入力しプロンプトで動かす（縦型ショート動画向け、リップシンク的）サービスを開発中。ただし顔の自由な生成は悪用リスクが大きく、踏み込まない可能性が高いとの見立て。
- このジャンルは掘り下げると常に「悪用リスク」に行き着く。既にフェイク生成が容易な状況であり、各社のせめぎ合いが続いている。

## 6. 大規模カンファレンスの所感（フィジカルAI・開発効率）

ある大規模技術イベントの報告。今年の軸は「AIエージェント」と「フィジカルAI」。

### フィジカルAI（現実世界×AI）

- 現実環境をセンサーで認識し、ロボットや自動運転車に活用する領域。
- 自動車メーカーの事例展示: 車両そのものの自動運転化ではなく、設計から製造・組み立て・テスト走行・販売に至る工程で専用ツールを活用し、開発時間を短縮できたという文脈。
- 物流系の展示: 棚に取り付けた縦長レールをロボットアームが上下し、必要なアイテムをピックアップして搬送機に渡す。従来は人手が必要だった「搬送機への載せ替え」工程も不要になりつつある。さらに工場周辺の配送・トラックまで含めた全体の機械化を目指す構想（大型模型展示）。
- 遠隔操作ロボット: 人間の腕にセンサーを装着し、人型ロボットに手・指の動きを反映させてスポンジ等を運ばせるデモ。外科手術の遠隔操作（ダヴィンチ的）イメージ。
- 蹴られても倒れない二足歩行ロボットの展示。

### 開発スピード・コスト

- 開発スピードが劇的に向上。企業レベルのプロトタイプ作成が、従来は早くて半年かかっていたものが1日でできる例も。
- それに伴い、人件費・ツール費を含む数百万円規模のコストが、日割り換算で大幅に圧縮される（ツール費が日割りで数百円規模）という指摘。

### 関連トピック

- 「5年以内に難しい外科手術を完璧にロボットができるようになる」という著名人の発言が話題に。実現可能性はありそうだが、「最初の患者になるのは誰か」という不安も。
- これに対し「そこも学習。人が経験から学んできたのと同じ」という意見。

## まとめ・キーワード

- 複数モデルの併用は強力だが「混ぜると危険」。前提条件・必要情報をいかに与えるかが本質。
- フロントエンド特化サービスの強みは「作り込まれた前提・テンプレート」にある。
- クラウド経由のモデル利用は、セキュリティ要件下での有力な選択肢。
- ノーコードはAI時代に相対的にしんどい領域。MCP・DevTools連携・スクショ活用が突破口。
- 今年の潮流は「AIエージェント」と「フィジカルAI」。開発スピードとコストのインパクトが大きい。
